方向键 / 空格翻页
分润机制理解与思考

从“数据交易”改写成“诊疗方案商城”

把复杂问题重新定义：我们卖的不是数据，而是疑难病诊疗方案；数据是方案的高质量好评；分润是新买家给老买家的长期返佣。

这次 slides 的目的：让业务团队先理解故事，再讨论比例和开发范围。

这次真正的变化：不是方案更复杂，而是问题被改写了

之前的设计越做越重，是因为我们把它当成“数据资产交易系统”。现在先把它讲成用户能理解的健康商城。

问题重构

旧问题

如何把患者数据确权、脱敏、交易、上链，并按贡献权重给多方分钱？

贡献权重表 区块链确权 数据交易所 隐私计算

新问题

如何让一个卖诊疗方案的健康商城跑起来，并让真实用过方案的人持续获得返佣？

方案商城 真实好评 订单分润 周清算
关键判断：复杂度来自错误问题，而不是来自业务本身01

三个实体，用电商语言就能讲清楚

不用先讲“数据资产”“三权分置”“区块链”。先让人知道平台里到底谁卖、谁买、谁分润。

电商类比
平台元素电商类比真实含义分润关系
商城淘宝 / 京东上架的是疑难病诊疗方案平台提供交易、审核、消息、客服和结算基础设施
方案运营方商家医院、医生、机构负责履约拿订单主收入，例如 70%
老用户高质量好评者用过方案并留下疗效数据后续新订单给他们返佣
现在用户新买家浏览方案、看疗效、下单购买付款触发本次分润
一句话：卖的是方案，数据是好评，分润是长期返佣。
这句话能消除前面 80% 的技术和合规焦虑02

故事怎么发生：王先生不是来买数据，他是来买方案

这页把用户旅程拆开。新用户看到老用户的疗效数据，就像看商品评价，最终购买的是方案本身。

用户故事
1
浏览商城王先生进入平台，按病种、阶段、预算筛选诊疗方案。
2
查看疗效背书他看到老用户的指标变化、治疗经历、匿名反馈。
3
付款买方案订单的主收入给医生/机构，站内信提醒履约和补材料。
4
治疗后入池王先生完成治疗、上传反馈，审核结果通过站内信通知。
交易物：诊疗方案。展示物：疗效好评。分润对象：用过该方案的老用户，不是卖个人数据。03

飞轮闭环：一个用户走完流程，就新增一个好评数据点

这套机制不是一次性返利，而是让真实疗效沉淀成后续销售的信任资产。

增长机制
诊疗方案
信任飞轮
现在用户付款真实订单触发收入，而不是投资入金。
完成治疗方案运营方交付服务，消息中心提醒补材料。
成为老用户上传疗效反馈，审核结果站内信留痕。
获得后续分润新订单越多，老用户越有动力推荐。
数据池越大，方案越可信；方案越可信，订单越多；订单越多，老用户越愿意参与。05

判断谁分润，只需要一个最小规则

MVP 不要做贡献者权重表。先用最容易解释的规则：是否真实用过方案 X。

极简规则

进入老用户池

用户在平台买过方案 X，完成方案服务，并通过基础审核上传疗效反馈；认证结果进入站内信。

真实订单 完成履约 有效反馈

不进入老用户池

没有真实订单、只注册未消费、上传材料无法验证，或者方案不是 X。

空挂身份 跨方案蹭池 刷好评

MVP 阶段先砍掉

贡献者权重表、浏览路径追溯、数据脱敏交易、区块链、TEE、数据交易所对接。它们不是没有价值，而是不属于第一版闭环。

最小可解释原则：用过方案 X，就参与方案 X 的老用户池。06

角色地图：每个角色拿什么钱，要分清楚

分润机制混乱，往往是因为把商家收入、推荐佣金、老用户返佣、平台抽成混成了一池钱。

参与方

现在用户

普通买家。付款购买方案，触发一次订单分账。

老用户

好评者。用过该方案，后续新订单从老用户池拿收益。

方案运营方

商家。负责方案上架、履约、售后，拿订单主收入。

B 端代理人

帮老人、农村患者管理身份和钱包，按协议抽代理服务费。

推荐人 R

带来新客户，拿一层推荐佣金，不做多级返佣。

平台

提供商城、订单、消息、客服、风控、结算和规则治理。

建议口径：R 拿销售佣金，老用户拿好评返佣，运营方拿方案收入。07

B 端代理人：不是卖货商家之外的附属角色

很多患者不会使用 APP、不会上传材料、不会提现。机构代理人可以成为真实的服务入口。

代理场景

他们帮患者做什么

注册、确认方案历史、查看站内信、上传疗效材料、维护老用户身份、查看收益、协助提现。

他们怎么赚钱

不是从所有新订单抽层级佣金，而是从被代理患者的收益中按协议抽服务费，例如代理收益的 10%。

为什么重要

它把低数字化能力患者纳入系统，同时给线下医疗机构一个可执行的业务角色。

B 端代理人的价值是履约和代管，不是发展下线。08

MVP 数据对象：不要为 V3 的叙事建第一版系统

第一版只需要支持“方案、订单、老用户池、推荐关系、结算记录”。

区块链是第二个故事：分润权二级市场

它不是 MVP 的交易核心，而是未来把长期返佣收益权金融化的叙事和工具。

V2 / V3

普通患者视角

老用户 A 慢慢收方案 X 的后续返佣。如果他不想等，可以把未来分润收益权一次性卖给投资者 B。

区块链真正有用处

证明这份未来收益权现在归 B，不归 A；后续新订单结算时自动打到 B 的钱包，避免双花和篡改。

1
A 收分润A 是方案 X 的老用户。
2
A 想套现不想等未来长尾收益。
3
B 买断双方协商一次性价格。
4
权属上链证明未来收益权转移。
5
后续结算新订单分润进入 B 钱包。
对 CEO 和资本市场可以讲，但不要让它拖慢 MVP。11

风险不是没有，但风险点已经变得更清楚

从“数据交易是否合法”转成“健康服务电商加返佣如何合规”。问题变窄，才有办法处理。

风险边界

老用户池稀释

人数过多后，每个老用户只能分到几毛钱。

先均分验证，后续加最近 N 人或质量阈值。

刷好评作弊

商家可能制造虚假老用户。

老用户身份必须来自真实订单和可验证疗效材料。

法律定性

新用户付款给老用户，可能被质疑为返利或集资。

每笔分润对应真实方案交付，且无多层级。

推荐人边界

R 15% 如果给个人，涉及税务和分销边界。

实名签约、税务申报、不做推荐人的推荐人。
法务仍然要问，但问题已经具体到比例、层级和订单真实性。13

产品结论：消息中心是业务状态机的一部分，不是单独的通知模块。17

审核员后台：不是一个“通过按钮”，而是多个证据队列

机构、医生、方案、老用户反馈、客服争议不能混在同一个审核里。每类审核看的证据、拒绝原因、影响状态都不同。

审核后台
机构资质审核
  • 看营业执照、服务范围、客服电话、结算主体。
  • 通过后才允许创建可提交方案。
  • 拒绝原因回到机构入驻页。
operators
医生资质审核
  • 看身份证、手机号、执业证、职称、合作授权。
  • 决定前台医生名称和资质怎么展示。
  • 敏感证件只给后台可见。
doctor_profiles
方案发布审核
  • 医学内容、宣传合规、价格、退款、分润比例。
  • 通过后发布 v1；不通过必须写原因。
  • 每次发布形成版本快照。
audit_tasks
老用户认证审核
  • 核对订单、履约节点、复查报告、脱敏预览。
  • 通过才进入有效老用户池。
  • 拒绝时不展示、不分润。
old_user_certifications
客服争议复核
  • 看工单、聊天记录、服务日志、上传材料。
  • 可触发退款、补服务、冻结分润。
  • 争议结果回写订单。
support_tickets
风控标记
  • 异常推荐、重复报告、批量好评、退款异常。
  • 可暂停展示、暂停提现、要求二次复核。
  • 保留审核日志。
risk_flags
后台设计标准：每一个“不过”都要有可复用原因码，不能只写一句人工备注。18

最高 Admin：管规则和审计，不应该日常替审核员点按钮

最高 admin 的重点不是“什么都能改”，而是控制规则版本、权限边界、高危操作和财务审计。否则后面无法解释谁改了分润。

超级后台
角色与数据权限

配置审核员、客服、机构运营、财务、超级管理员。不同角色只能看自己任务和数据范围。

rbac_roles
分润规则版本

维护 70/15/10/5、生效时间、适用类目、冻结期。订单只引用当时有效版本。

split_rules
审核策略配置

定义哪些字段必填、哪些病种必二审、拒绝原因库、审核 SLA 和自动派单规则。

audit_policies
结算批次与回滚

查看批次、冻结金额、提现失败、退款扣回。高危回滚需要双人复核和财务理由。

settlement_batches
风控阈值

设置同设备注册、同报告重复、异常推荐转化、退款率阈值，命中后暂停分润或提现。

risk_rules
消息模板与审计

管理站内信模板、客服话术、触达规则；导出订单、分润、审核、提现、客服记录。

message_templates / audit_logs
推断结论：最高 admin 页面要少做“直接改业务数据”，多做“规则版本、审批、日志、回滚”。19

互相查证矩阵：页面、后台、数据库必须能对上

这页是给产品经理和开发对需求用的。任何一个页面如果找不到后台任务、数据库写入和异常状态，就说明还没想细。

最后用一张图收束：推荐的闭环

这张图是对外讲故事时最应该保留的版本。

最终模型
1
现在用户买诊疗方案真实订单产生收入，方案运营方负责履约。
2
老用户疗效作为好评展示数据不是被单独出售，而是增强方案可信度。
3
订单拆出分润池推荐人、老用户池、平台分别拿不同的钱。
4
新用户治疗后变成老用户上传反馈后进入同方案用户池。
5
飞轮继续转更多真实好评带来更多订单，更多订单带来更多返佣。
推荐表达：这是一个“带长期返佣机制的诊疗方案商城”，不是一个第一天就要上链的数据交易所。

给团队的提醒

不要急着证明愿景很大。先证明一个用户愿意买方案、一个老用户愿意上传好评、一次周清算能准确到账。

最小闭环跑通后，再谈加权算法、二级市场、区块链和数据交易所。21
