03 Architecture

技术架构：先让交易和分润跑起来

底层定位是健康数据资产平台，但 MVP 技术重点不是先搭建数据交易所或完整区块链资产系统，而是稳定处理方案展示、下单支付、服务履约、老用户反馈、订单拆账、钱包台账、结算审核和退款回滚；确权与上链先以轻量方式实现，作为资产收益的依据。

看 MVP 系统 Slides 下一章：功能模块

MVP 技术目标：商城、订单、审核、分账、钱包、后台形成闭环。

1. MVP 系统边界

C 端用户 App / H5

浏览方案、查看老用户反馈、下单支付、提交随访反馈、查看收益和提现状态。

方案运营方后台

维护方案信息、价格、适用范围、履约节点、订单服务状态和售后记录。

运营审核后台

审核方案、审核老用户反馈、处理异常订单、冻结收益、发起结算批次。

分润结算引擎

根据订单、推荐关系、老用户池和退款状态生成分账明细与钱包台账。

支付与钱包

接入支付通道，维护用户余额、冻结金额、可提现金额、提现申请和财务导出。

风控与审计日志

记录关键操作、审核证据、推荐关系变更、代理授权、结算批次和回滚动作。

2. 业务流程架构

1

方案上架

运营方提交方案，平台审核适用人群、服务内容、价格和风险提示。

2

用户购买

用户通过推荐链接或自然流量下单，订单记录推荐人和价格快照。

3

服务履约

运营方更新服务节点，平台根据完成状态决定是否进入可结算。

4

生成分账

结算引擎按订单比例生成运营方、推荐人、老用户池、平台台账。

5

清算提现

过退款期后批量清算，用户或机构可按财务规则提现。

3. 核心数据对象

对象 关键字段 说明

4. 结算引擎规则

订单完成
识别推荐人
计算老用户池
生成台账
  1. 只有订单状态达到 completed，并且没有处于退款争议时，才进入待结算。
  2. 读取订单价格快照，按当前生效费率生成分账，不回溯受后续费率修改影响。
  3. 推荐人 R 只取订单绑定的一级推荐关系；若无推荐人，则按总裁规则进入老用户池或平台营销池。
  4. 老用户池从 plan_user_pool 中筛选 share_status=active 的有效成员。
  5. MVP 采用均分，金额保留到分，尾差进入平台调节账户或下一批次。
  6. 分账先写入冻结钱包流水，过 T+7 或退款期后转为可提现。
  7. 退款、投诉成立、作弊识别时，按订单关联的 settlement_items 反向生成回滚流水。

5. 权限和后台角色

角色 能做什么 不能做什么
平台超级管理员 配置费率、结算周期、风控规则、后台账号。 直接改钱包余额，必须通过审核流和流水。
运营审核员 审核方案、反馈、老用户池资格和异常订单。 修改财务结算参数。
方案运营方 维护自己的方案、查看自己的订单和服务状态。 查看其他机构订单、修改分润规则。
B 端代理人 在授权范围内协助被代理用户提交反馈、查看代理服务费。 代替用户承诺收益、伪造材料、转移用户钱包。
财务 查看结算批次、导出付款表、处理提现。 修改方案内容和医学反馈。

6. V2/V3 才考虑的技术能力

质量加权算法

基于反馈完整度、时间窗口、复诊结果、平台审核分，对老用户池做差异化分配。

分润权二级市场

老用户未来可选择长期收返佣，或一次性转让未来收益权。这里才需要链上凭证和交易规则。

数据资产专项能力

在明确合规路径后，再做数据脱敏、授权管理、可信计算、数据交易所适配。

架构原则：MVP 所有分润都从真实订单出发，任何没有订单、没有授权、没有审核材料的“收益权”都不进入系统。
